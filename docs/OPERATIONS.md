# Регламент безопасного запуска

1. Зафиксировать неизменяемую копию Excel и её SHA-256.
2. Выполнить `validate`; проверить ошибки до обращения к API. В финальном файле ожидаются три предупреждения `licence_end_inferred`; они не блокируют запуск.
3. Выполнить dry-run и проверить `plan.json`/`payloads.jsonl`.
4. Выполнить `auth` для нужного профиля.
5. На PSI запустить `--execute --limit 1 --operator-mode`.
6. В UI и API проверить лицензию, историю и ровно одну `active`-запись.
7. Расширить PSI-запуск на весь файл и сохранить каталог `runs/psi/...`.
8. Повторить dry-run для PROD и только затем использовать `--execute --confirm-prod`.

## Ошибки и компенсация

В обычном режиме ошибочная группа фиксируется в checkpoint, затем обработка продолжается. В операторском режиме доступны retry, skip и abort. Успешные группы при повторе не создаются заново.

Перед записью лицензии проверяется субъект. При отсутствии карточки `organizations` он собирается из Excel. Если в итоге не хватает обязательных полей, группа получает статус `skipped` без обращений на создание/обновление. Откат пропущенной группы ничего не изменяет; в итоге rollback выводит количество `skipped_groups`.

При повторной обработке ранее пропущенной или ошибочной группы старые поля `reason` и `error` удаляются после перехода в `running`/`completed`, поэтому checkpoint отражает актуальный результат.

Если новая `active`-запись создана, но перевод старой в `reissued` упал, мигратор пытается восстановить прежние статусы и удалить новую запись. Неудачная компенсация отдельно попадает в лог; затем применяется checkpoint rollback.

Фактический rollback после каждого успешно восстановленного или удалённого документа сохраняет прогресс в `checkpoint.json`. Рядом создаётся `rollback-report.json`. Прерванный откат можно запустить той же командой повторно: уже обработанные документы пропускаются. После завершения checkpoint получает `rollback.status = completed`, и дальнейшие повторы ничего не изменяют.

Для каждой лицензии финальная проверка ищет записи по `licenseId + status=active`. Успех возможен только при одной активной записи, совпадающей с последней записью плана.

Cookie и JWT не передаются через параметры и не попадают в Git. Файлы `auth/<profile>/cookie.md` и `token.md` перечитываются после первого 401/403.

Для стенда с ведомственным сертификатом сохраните доверенную CA-цепочку в
`auth/<profile>/ca.pem` либо укажите `--ca-bundle`. Не используйте
`--no-verify-tls` с рабочими cookie/JWT: он предназначен только для диагностики
без передачи учётных данных.
